# 報表分類新增與管理：規劃審查

- **狀態：** NEEDS_REVISION（待確認三項業務規則後才可進入開發）
- **專案邊界：** `frontend/` 的報表管理、分類選取與 Mock RBAC 模型；不實作、不串接 API、不做資料遷移。
- **模式／profile／風險／深度：** plan／web／medium／standard。
- **角色：** PM（需求與驗收）、UI/UX（操作流程與無障礙）、Lead Developer（資料模型與整合邊界）、QA（驗收與回歸案例）。CEO 不適用。

> **追溯更新（2026-09-03）：** Project Decisions 的 PD-026 已核准獨立 Category Master 與系統保留分類「待分類 / 未分類」。本文件中「有引用時禁止硬刪除」及「先重新指派後刪除」的建議，已由 PD-026 取代；最新規則為刪除前先將關聯 Report 搬移至「待分類 / 未分類」、清除舊分類權限後刪除原分類。其餘歷史分析保留供追溯。

## 現況證據與結論

目前 `MockReport.Category` 是自由字串；`MockRbacService.ReportCategories` 由現存報表反推，且角色的分類權限也用同一個字串作索引。故新增一個空分類無法被保存，重新命名會讓既有授權失聯，停用／刪除又會影響可執行報表。

**架構決策：** 將分類改為獨立主資料，以不可變的 `CategoryId` 作為報表與權限的關聯鍵；名稱只作顯示與搜尋，不作授權索引。

## V1 產品範圍

### 使用者與目標

- 報表管理員可建立、搜尋、編輯、啟用／封存分類，並看見各分類的報表數量與狀態。
- 報表管理員可在新增／編輯報表時，從可指派分類清單選擇分類。
- 權限管理員可為角色設定分類層級的執行、匯出 PDF、列印權限。

### 納入

- 扁平分類（無階層）、名稱、說明、狀態、排序、建立／更新資訊與關聯報表數。
- 分類清單、建立／編輯 Modal、封存／復用與受保護的刪除流程。
- 報表編輯器與角色權限編輯器改以分類 ID 關聯。
- 前端層級的輸入、衝突、關聯與權限錯誤回饋；操作紀錄的資料契約。

### 不納入 V1

- 多層分類、跨組織／多語系分類、批次匯入／匯出、正式後端 API、資料庫遷移的實作、歷史報表版本化。

## 建議業務規則

1. `CategoryId` 建立後不可修改；顯示名稱須 trim 後不可空白，且以 Unicode 正規化、大小寫／全半形規則判定唯一。
2. 啟用分類可供新報表指派；封存分類不可再指派，但既有報表仍保留分類與可見的「已封存」標示。
3. 禁止硬刪除仍被報表或角色權限引用的分類。管理者須先重新指派報表，並移除或轉移角色權限；未被引用者才可硬刪除。
4. 報表是否可被一般使用者看到，應由「報表啟用 + 分類存在 + 分類權限可執行」共同決定；是否讓封存分類下既有報表繼續執行，需產品決策。
5. 所有 Modal 驗證與關聯衝突必須以欄位下方或 Modal 內 Form Alert 顯示；錯誤不可關閉 Modal，也不可寫入背景頁面的 Notice／Toast。
6. 分類管理權限建議獨立為 `ReportCategoryManagement`，而非只沿用廣義的 `RptManagement`；過渡期可由 `RptManagement` 授權。

## 資料與整合設計

### 建議主資料

`ReportCategory`：`id`、`name`、`description?`、`status (Active|Archived)`、`sortOrder`、`createdAt`、`createdBy`、`updatedAt`、`updatedBy`、`version`。

報表應儲存 `categoryId`（read model 可展開 `categoryName`）；角色權限應儲存 `roleId + categoryId + permission flags`。API 應由服務端以版本或 ETag 避免兩位管理者覆寫同一筆分類。

### 未來 API 契約

- `GET /admin/report-categories?query=&status=&page=`：清單、關聯報表數與頁碼。
- `POST /admin/report-categories`、`PATCH /admin/report-categories/{id}`：建立／編輯；回傳欄位錯誤與 version conflict。
- `POST /admin/report-categories/{id}/archive`、`POST /.../restore`：狀態異動。
- `GET /admin/report-categories/{id}/impact`：刪除前報表／角色權限影響。
- `DELETE /admin/report-categories/{id}`：僅 zero-reference；重新分類應是明確的獨立命令。

## UI/UX 方案

建議在既有「報表管理」增加次分頁：**報表清單｜分類管理**，保留單一管理入口與既有操作脈絡。

- 分類管理頁：搜尋、狀態篩選、`新增分類`；表格顯示名稱／說明／關聯報表數／狀態／更新時間／操作。
- 建立／編輯 Modal：名稱為必填、說明與排序為選填；欄位錯誤就地顯示，提交失敗仍停留 Modal。
- 封存：確認 Dialog 顯示「不再可供新報表選用」及關聯數；封存成功以頁面內成功狀態或短暫 Toast 提示。
- 刪除：先顯示 impact；有引用時停在 Dialog，提供「前往重新指派」而非允許刪除。
- 報表編輯器：只列出啟用分類；編輯既有報表時，已封存的原分類可保留顯示並標記。
- 可及性：Dialog 使用 `aria-modal`、標題與 error summary 關聯；錯誤時 focus 進入 summary／第一個無效欄位；不可只用顏色表達封存或錯誤。

## 版本、里程碑與驗收

| Version | Milestone | Feature / Task | 複雜度 | 相依性 | 驗收條件 |
| --- | --- | --- | --- | --- | --- |
| V1 MVP | M1 資料契約 | 定義分類 ID、狀態與報表／角色權限關聯 | High | 刪除與封存規則 | 分類可在無報表時存在；改名不改變授權關聯。 |
| V1 MVP | M2 管理流程 | 分類清單、建立、編輯、封存、影響預覽 | Medium | M1、管理權限 | 無效輸入／重名／關聯衝突皆留在目前 Modal。 |
| V1 MVP | M3 既有流程整合 | 報表選分類、角色分類權限與清單篩選改用 ID | High | M1、M2 | 啟用分類可新指派；封存分類不出現在新指派選項。 |
| V1.1 | M4 營運品質 | API 授權、審計、併發衝突、回歸測試 | High | 後端 owner | 未授權操作被拒絕；每次分類生命週期異動可稽核。 |

**估算前提：** 尚無正式 API／資料庫，以下僅為有一位前端、一位後端與產品決策及時到位時的工程工作量：樂觀 5–7 人日、合理 8–12 人日、保守 15–20 人日。變異主要來自既有報表與權限資料的遷移規則、封存後可執行性的決策及審計需求。

**關鍵路徑：** 先確認生命週期規則 → 建立穩定 ID 與後端契約 → 報表／權限關聯遷移 → 管理 UI → 回歸驗證。UI 原型可與資料契約並行；不可在 ID 與刪除規則未定前實作 CRUD。

## 風險與待決策

| 風險／問題 | 影響 | 建議決策 |
| --- | --- | --- |
| 分類改名仍使用名稱作 key | 權限消失或報表不可見 | 一律改用不可變 `CategoryId`。 |
| 封存分類下的既有報表 | 可能意外下架報表 | 建議「不可新指派、既有報表仍依報表啟用與權限決定」；請產品確認。 |
| 有引用的刪除 | 產生孤兒資料或權限遺失 | 預設禁止；提供 impact 與顯式重新指派。 |
| 分類結構 | 多層分類會擴大權限繼承與導覽複雜度 | V1 固定扁平；層級需求移至 V2。 |
| 正式授權 | 現況僅為 Mock，前端守衛不是安全邊界 | 由後端實作授權、完整性與審計。 |

## 開發就緒判定

1. 封存分類下，既有啟用報表是否仍可執行？
